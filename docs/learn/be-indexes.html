الفهارس في قواعد البيانات: لماذا يتحول استعلامك من ثوانٍ إلى ملي ثانية

Database indexes: why a query drops from seconds to milliseconds

شرح بنية B-Tree، وترتيب الأعمدة في الفهرس المركب، والانتقائية، ومتى يضر الفهرس بدل أن ينفع.

backendintermediate⏱ 22 دقيقة

لماذا يهمك؟

أكثر مشكلة أداء شائعة في الأنظمة الحقيقية هي استعلام يمسح الجدول كاملًا. فهم الفهارس هو أرخص تحسين أداء موجود.

The most common production performance problem is a query scanning a whole table. Indexes are the cheapest performance win available.

ما هو الفهرس فعليًا

الفهرس بنية إضافية مرتبة، غالبًا شجرة B-Tree، تخزن قيم عمود مع مؤشرات إلى صفوفها. بدلًا من قراءة ملايين الصفوف تنزل قاعدة البيانات في الشجرة بعدد قليل من القفزات. الثمن أن كل إدخال أو تحديث يجب أن يحدّث الفهرس أيضًا، وأن الفهرس يشغل مساحة على القرص وفي الذاكرة، لذا الفهرس قرار موازنة بين سرعة القراءة وتكلفة الكتابة.

What an index really is

An index is an extra ordered structure, usually a B-Tree, holding column values with pointers to their rows. Instead of reading millions of rows the database descends the tree in a few hops. The price is that every insert or update must also maintain the index, and the index consumes disk and memory, so indexing is a trade between read speed and write cost.

الانتقائية وترتيب الأعمدة

الفهرس مفيد عندما يستبعد نسبة كبيرة من الصفوف. فهرس على عمود بقيمتين فقط نادرًا ما يستخدم. في الفهرس المركب يهم الترتيب: فهرس على (user_id, created_at) يخدم البحث بـ user_id وحده وبالاثنين معًا، لكنه لا يخدم البحث بـ created_at وحده. القاعدة: ضع أعمدة المساواة أولًا ثم عمود النطاق أو الترتيب أخيرًا.

Selectivity and column order

An index helps when it eliminates most rows. An index on a two-value column is rarely used. In a composite index order matters: an index on (user_id, created_at) serves filters on user_id alone and on both together, but not on created_at alone. Rule: equality columns first, the range or sort column last.

اقرأ خطة التنفيذ

لا تخمّن، اقرأ الخطة. في PostgreSQL يكشف EXPLAIN ANALYZE عن Seq Scan مقابل Index Scan، وعن الفرق بين التقدير والواقع، وعن عدد الصفوف المزالة بالفلتر. فرق كبير بين المقدر والفعلي يعني إحصاءات قديمة تحتاج ANALYZE. وجود Seq Scan على جدول كبير مع فلتر انتقائي هو أوضح إشارة إلى فهرس مفقود.

Read the execution plan

Do not guess, read the plan. In PostgreSQL, EXPLAIN ANALYZE reveals Seq Scan versus Index Scan, the gap between estimated and actual rows, and how many rows the filter removed. A wide estimate gap means stale statistics that need ANALYZE. A Seq Scan on a large table with a selective filter is the clearest sign of a missing index.

متى يضر الفهرس

الإفراط في الفهارس يبطئ الكتابة ويستهلك الذاكرة ويربك المخطط. كذلك تعطّل الدوال المطبقة على العمود استخدام الفهرس، فمثلًا WHERE lower(email) = ... لن يستفيد من فهرس عادي على email بل يحتاج فهرسًا تعبيريًا. وفي الجداول الصغيرة يكون المسح الكامل أسرع أصلًا، لذلك لا تضف فهرسًا بلا قياس قبل وبعد.

When an index hurts

Too many indexes slow writes, eat memory and confuse the planner. Functions applied to a column also disable index use: WHERE lower(email) = ... cannot use a plain index on email and needs an expression index. On small tables a full scan is faster anyway, so never add an index without measuring before and after.

مثال عملي · من مسح كامل إلى فهرس مركب مع قياس الخطة

-- Slow: filters by user and sorts by date on a large table
EXPLAIN ANALYZE
SELECT id, total FROM orders
WHERE user_id = 42 AND created_at >= now() - interval '30 days'
ORDER BY created_at DESC
LIMIT 20;
-- Seq Scan on orders  (actual rows=3_000_000)

-- Equality column first, range/sort column last
CREATE INDEX CONCURRENTLY idx_orders_user_created
  ON orders (user_id, created_at DESC);

ANALYZE orders;   -- refresh planner statistics, then EXPLAIN again

أخطاء شائعة

  • إضافة فهرس لكل عمود فتصبح الكتابة بطيئة بلا فائدة قراءة.
  • تطبيق دالة على العمود في شرط WHERE فيُعطَّل الفهرس.
  • بناء فهرس على جدول إنتاجي بدون CONCURRENTLY فيُقفل الجدول.
  • Indexing every column, making writes slow with no read benefit.
  • Wrapping the column in a function inside WHERE, disabling the index.
  • Building an index on a production table without CONCURRENTLY and locking it.

تمرين تطبيقي

حسّن استعلام تقارير بطيء على جدول فيه ملايين الصفوف.

  1. شغّل EXPLAIN ANALYZE وسجّل نوع المسح والزمن الفعلي.
  2. أضف فهرسًا مركبًا يبدأ بأعمدة المساواة وينتهي بعمود الترتيب.
  3. أعد القياس وقارن، ثم احذف أي فهرس لم يُستخدم فعلًا.

معيار النجاح: تحول الخطة إلى Index Scan وانخفاض الزمن بمقدار مرتبة أو أكثر.

اختبر نفسك

1. فهرس على (user_id, created_at) يخدم أي استعلام؟
An index on (user_id, created_at) serves which query?

الفهرس المركب يُقرأ من اليسار، فيخدم العمود الأول ثم ما يليه.

2. لماذا لا يستفيد WHERE lower(email) = 'a@b.com' من فهرس عادي على email؟
Why does WHERE lower(email) = 'a@b.com' not use a plain index on email?

يحتاج الأمر فهرسًا تعبيريًا على lower(email).
