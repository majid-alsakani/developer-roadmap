الجلسات والتوكن: تصميم مصادقة آمنة بلا أوهام

Sessions and tokens: designing authentication without illusions

الفرق بين الجلسة والتوكن، لماذا لا يمكن إبطال JWT بسهولة، وأين تُخزّن التوكنات بأمان.

backendadvanced⏱ 20 دقيقة

لماذا يهمك؟

أخطاء المصادقة لا تظهر في الاختبارات بل في الاختراقات. التصميم الصحيح من البداية أرخص بكثير من الترقيع لاحقًا.

Authentication mistakes do not show up in tests, they show up in breaches. Designing it right is far cheaper than patching later.

الجلسة مقابل التوكن

في نموذج الجلسة يحتفظ الخادم بسجل الجلسة ويعطي المتصفح معرفًا داخل كوكي. في نموذج JWT يحمل التوكن نفسه البيانات موقّعة، فلا يحتاج الخادم إلى بحث. الفرق الجوهري في الإبطال: حذف صف الجلسة ينهي الوصول فورًا، بينما يبقى JWT صالحًا حتى انتهاء صلاحيته ما لم تبنِ قائمة إبطال، وهي عمليًا عودة إلى حالة على الخادم.

Session versus token

With sessions the server keeps a session record and hands the browser an id in a cookie. With JWT the token itself carries signed claims, so no lookup is needed. The crucial difference is revocation: deleting a session row ends access instantly, while a JWT stays valid until it expires unless you maintain a denylist, which is effectively server state again.

توكن وصول قصير وتوكن تجديد

التصميم العملي: توكن وصول قصير العمر من خمس إلى خمس عشرة دقيقة، وتوكن تجديد طويل مخزّن على الخادم وقابل للإبطال، مع تدوير التوكن عند كل تجديد. إذا استُخدم توكن تجديد قديم مرتين فهذه إشارة سرقة تستوجب إنهاء كل جلسات المستخدم. هذا يوازن بين قابلية التوسع وبين القدرة الحقيقية على قطع الوصول.

Short access token plus refresh token

The practical design: a short-lived access token of five to fifteen minutes, plus a long-lived refresh token stored server-side and revocable, rotated on every refresh. If an old refresh token is replayed, treat it as theft and invalidate all of that user's sessions. This balances scalability with a real ability to cut access off.

أين تُخزَّن التوكنات

تخزين التوكن في localStorage يعرّضه لأي ثغرة XSS لأن أي سكربت يستطيع قراءته. الأفضل كوكي بخصائص HttpOnly و Secure و SameSite، فلا يصل إليه جافاسكربت، مع حماية من CSRF عبر SameSite أو توكن مضاد. وتذكّر أن محتوى JWT مقروء للجميع لأنه مشفّر بالترميز لا بالتعمية، فلا تضع فيه أسرارًا.

Where tokens are stored

Storing a token in localStorage exposes it to any XSS flaw, because any script can read it. Prefer a cookie with HttpOnly, Secure and SameSite so JavaScript cannot touch it, combined with CSRF protection via SameSite or an anti-forgery token. Remember a JWT payload is merely encoded, not encrypted, so never put secrets in it.

التحقق الصارم من التوقيع

ثبّت الخوارزمية على الخادم ولا تثق بحقل alg القادم من التوكن، فهجوم alg=none أو تبديل RS256 بـ HS256 هجوم كلاسيكي. تحقق أيضًا من المُصدر والجمهور وزمن الانتهاء، واستخدم مقارنة ثابتة الزمن. أخيرًا ضع خطة تدوير للمفاتيح مع معرف مفتاح kid حتى تستطيع تغيير المفتاح دون إخراج كل المستخدمين.

Strict signature verification

Pin the algorithm on the server and never trust the token's own alg field; alg=none and RS256-to-HS256 confusion are classic attacks. Also verify issuer, audience and expiry, and use constant-time comparison. Finally plan key rotation with a kid header so you can change keys without logging everyone out.

مثال عملي · تحقق صارم من JWT مع خوارزمية مثبّتة

import jwt  # PyJWT

def verify(token: str) -> dict:
    return jwt.decode(
        token,
        key=PUBLIC_KEY,
        algorithms=["RS256"],      # pinned; never read alg from the token
        audience="api.example.com",
        issuer="https://auth.example.com",
        options={"require": ["exp", "iat", "sub"]},
    )

# Cookie flags that keep the token away from JavaScript
response.set_cookie(
    "access_token", token,
    httponly=True, secure=True, samesite="lax", max_age=900,
)

أخطاء شائعة

  • تخزين التوكن في localStorage فيسرق بأي ثغرة XSS.
  • توكن وصول طويل العمر بلا آلية إبطال حقيقية.
  • قبول الخوارزمية المذكورة داخل التوكن نفسه.
  • Storing tokens in localStorage where any XSS can steal them.
  • Long-lived access tokens with no real revocation path.
  • Trusting the algorithm declared inside the token itself.

تمرين تطبيقي

صمّم مصادقة لتطبيق ويب مع تسجيل خروج فوري من كل الأجهزة.

  1. اجعل توكن الوصول قصيرًا وخزّن توكن التجديد في جدول قابل للإبطال.
  2. دوّر توكن التجديد عند كل استخدام واكتشف إعادة الاستخدام.
  3. انقل التوكنات إلى كوكي HttpOnly وأضف حماية CSRF.

معيار النجاح: الضغط على تسجيل الخروج من كل الأجهزة يقطع الوصول خلال دقائق معدودة على الأكثر.
