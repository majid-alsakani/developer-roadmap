التزامن في جافاسكربت: حلقة الأحداث والوعود بعمق

Asynchrony in JavaScript: the event loop and promises in depth

نموذج ذهني دقيق لحلقة الأحداث وطوابير المهام الدقيقة والكبرى، وكيف يترجم async/await إلى وعود.

frontendintermediate⏱ 20 دقيقة

لماذا يهمك؟

أغلب الأخطاء الغريبة، مثل ترتيب غير متوقع أو نتيجة قديمة، سببها فهم ناقص لحلقة الأحداث.

Most odd bugs, like unexpected ordering or stale results, come from a shaky event-loop model.

خيط واحد ومكدس واحد

تعمل جافاسكربت في المتصفح على خيط واحد بمكدس واحد، فأي عملية طويلة متزامنة تجمّد الواجهة كلها. لذلك تُسلَّم الأعمال الطويلة إلى واجهات المتصفح مثل fetch و setTimeout و Web Workers ويعود الناتج كمهمة في طابور. التزامن هنا ليس توازيًا: العمليات تتداخل زمنيًا لكنها لا تنفذ معًا على الخيط الرئيسي.

One thread, one stack

Browser JavaScript runs on one thread with one call stack, so any long synchronous operation freezes the whole UI. Long work is handed to browser APIs such as fetch, setTimeout and Web Workers and returns later as a queued task. Concurrency here is not parallelism: operations interleave in time but never run together on the main thread.

المهام الدقيقة قبل الكبرى

بعد إفراغ المكدس تنفذ كل المهام الدقيقة، مثل ردود الوعود، قبل أي مهمة كبرى مثل المؤقتات والأحداث. لهذا يظهر رد الوعد قبل مؤقّت بصفر ملي ثانية. وهذا سلاح ذو حدين: سلسلة وعود لا تنتهي تمنع المتصفح من الوصول إلى مرحلة الرسم فتتجمد الصفحة رغم أن الكود غير متزامن ظاهريًا.

Microtasks before macrotasks

Once the stack empties, all microtasks such as promise callbacks run before any macrotask such as timers and events. That is why a promise callback fires before a zero-delay timer. It cuts both ways: an endless promise chain starves the rendering step, so the page freezes even though the code looks asynchronous.

async/await ليس سحرًا

الدالة async ترجع وعدًا دائمًا، وكل await يقسم الدالة: ما بعده يُجدول كمهمة دقيقة عند استقرار الوعد. لذلك await داخل حلقة يعني طلبات متسلسلة بطيئة، بينما Promise.all يشغّلها معًا. استخدم try/catch حول await، وتذكر أن وعدًا مرفوضًا بلا معالج قد يسقط تطبيق الخادم.

async/await is not magic

An async function always returns a promise, and every await splits the function: the code after it is scheduled as a microtask when the promise settles. Awaiting in a loop means slow sequential requests while Promise.all runs them together. Use try/catch around await, and remember an unhandled rejection can crash a server runtime.

الإلغاء وسباقات الحالة

في البحث الحي يكتب المستخدم بسرعة فتنطلق عدة طلبات، وقد يصل الطلب القديم بعد الجديد فيكتب فوق النتيجة الصحيحة. الحل AbortController لإلغاء الطلب السابق أو حفظ معرف آخر طلب وتجاهل ما هو أقدم. هذه ليست حالة نادرة بل السبب الأول لظهور نتائج لا تطابق ما كتبه المستخدم.

Cancellation and race conditions

In live search users type fast and fire several requests; an older one may land after a newer one and overwrite the correct result. Fix it with an AbortController, or store the latest request id and ignore older responses. This is the top reason results stop matching the typed text.

مثال عملي · بحث حي بدون سباق حالة باستخدام AbortController

let controller;

async function search(term) {
  controller?.abort();               // cancel the previous in-flight request
  controller = new AbortController();
  try {
    const res = await fetch(`/api/search?q=${encodeURIComponent(term)}`, {
      signal: controller.signal,
    });
    if (!res.ok) throw new Error(`Search failed: ${res.status}`);
    render(await res.json());
  } catch (err) {
    if (err.name !== 'AbortError') showError(err);  // aborts are expected
  }
}

// Parallel instead of sequential:
const [user, orders] = await Promise.all([getUser(id), getOrders(id)]);

أخطاء شائعة

  • استخدام await داخل حلقة لطلبات مستقلة بدل Promise.all.
  • نسيان معالجة الرفض فيظهر unhandled promise rejection.
  • افتراض أن مؤقّتًا بصفر ينفذ قبل الوعود.
  • Using await in a loop for independent requests instead of Promise.all.
  • Forgetting rejection handling, producing unhandled rejections.
  • Assuming a zero-delay timer runs before promise callbacks.

تمرين تطبيقي

ابنِ حقل بحث حي يستدعي واجهة برمجية ويتحمل الكتابة السريعة.

  1. أضف تأخيرًا 250 ملي ثانية قبل إرسال الطلب.
  2. ألغِ الطلب السابق عبر AbortController مع كل حرف.
  3. اعرض حالات التحميل واللا نتائج والخطأ ثم اختبر بشبكة بطيئة.

معيار النجاح: النتائج المعروضة تطابق آخر نص كتبه المستخدم دائمًا.
