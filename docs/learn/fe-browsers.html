كيف يعرض المتصفح الصفحة: من البايت إلى البكسل

How the browser renders a page: from bytes to pixels

مسار العرض في المتصفح: التحليل، شجرة DOM و CSSOM، التخطيط، الرسم، والدمج، ولماذا يقرر ذلك سرعة موقعك.

frontendbeginner⏱ 18 دقيقة

لماذا يهمك؟

أغلب البطء والاهتزاز البصري ليس بسبب حجم الكود بل بسبب سوء فهم مسار العرض. من يفهمه يكتب واجهات أسرع بلا مكتبات إضافية.

Most slowness and jank is not bundle size but a misunderstood render path. Understanding it means faster interfaces with no extra libraries.

التحليل وبناء DOM

يحوّل المتصفح بايتات HTML إلى محارف ثم رموز ثم عقد ثم شجرة DOM. التحليل تدريجي فيمكن بدء العرض قبل اكتمال المستند، لكن أي وسم script بدون defer يوقف المحلل لأن السكربت قد يعدّل البنية. لهذا توضع السكربتات في نهاية الجسم أو تُعلّم بـ defer، وهذه النقطة وحدها تختصر مئات الملي ثانية من زمن ظهور أول محتوى.

Parsing and the DOM

The browser turns HTML bytes into characters, tokens, nodes and finally the DOM tree. Parsing is incremental so rendering can start early, but a plain script tag blocks the parser because it may mutate the document. Scripts therefore belong at the end of the body or carry defer; that single change often removes hundreds of milliseconds from first contentful paint.

CSSOM ومنع العرض

بالتوازي يبني المتصفح شجرة CSSOM، ولا يرسم شيئًا قبل معرفة الأنماط النهائية وإلا ظهر محتوى غير منسق ثم قفز. لذلك كل ملف أنماط في الرأس يؤخر أول رسم. الحل العملي: تقليل الأنماط الحرجة، ووضع أنماط الشاشة الأولى داخل الصفحة، وتحميل الباقي بشرط media أو بشكل مؤجل.

CSSOM and render blocking

In parallel the browser builds the CSSOM and paints nothing until final styles are known, otherwise unstyled content would flash. Every stylesheet in the head therefore delays first paint. The practical fix: shrink critical CSS, inline what the first screen needs, and load the rest with a media condition or lazily.

التخطيط والرسم والدمج

بعد دمج الشجرتين يحسب المتصفح موضع وحجم كل صندوق، ثم يرسم البكسلات، ثم يدمج الطبقات على وحدة الرسوميات. تغيير العرض أو الارتفاع يعيد التخطيط، وتغيير اللون يعيد الرسم فقط، بينما transform و opacity تعالجان في الدمج وحده. لهذا الحركات المبنية على transform أسلس بكثير من المبنية على top و left.

Layout, paint and compositing

After merging both trees the browser computes each box's position and size, paints pixels, then composites layers on the GPU. Width or height changes re-run layout, a color change only repaints, while transform and opacity are handled by the compositor alone. That is why transform animations are far smoother than top/left ones.

الاهتزاز والقياس القسري

يحاول المتصفح تسليم إطار كل ست عشرة ملي ثانية. إذا قرأت خاصية هندسية مثل offsetHeight مباشرة بعد كتابة نمط أجبرته على إعادة تخطيط فوري وسط الإطار. الحل فصل القراءات عن الكتابات: اقرأ القياسات كلها ثم طبّق التغييرات داخل requestAnimationFrame، ولوحة الأداء تُظهر هذه الحالات كأشرطة طويلة.

Jank and forced layout

The browser aims for a frame every 16 ms. Reading a geometric property such as offsetHeight right after a style write forces an immediate mid-frame layout. Separate reads from writes: measure everything first, then mutate inside requestAnimationFrame. The Performance panel shows these as long blocking bars.

مثال عملي · فصل القراءات عن الكتابات لتجنب إعادة التخطيط القسري

// BAD: read and write mixed, layout forced on every loop turn
for (const card of cards) {
  card.style.height = card.offsetHeight + 10 + 'px';
}

// GOOD: batch reads, then batch writes in one animation frame
const heights = cards.map((c) => c.offsetHeight); // 1) read phase
requestAnimationFrame(() => {
  cards.forEach((c, i) => {
    c.style.transform = 'translateY(0)';           // compositor friendly
    c.style.height = heights[i] + 10 + 'px';       // 2) write phase
  });
});

أخطاء شائعة

  • تحريك العناصر بـ top و left بدل transform فيتكرر التخطيط كل إطار.
  • سكربتات في الرأس بدون defer فتوقف تحليل المستند.
  • خطوط ضخمة بدون font-display فيختفي النص ثوانٍ.
  • Animating with top and left instead of transform, forcing layout every frame.
  • Scripts in the head without defer, blocking document parsing.
  • Heavy fonts without font-display, leaving invisible text for seconds.

تمرين تطبيقي

خذ صفحة فيها مئتا بطاقة وحسّن زمن أول رسم وسلاسة التمرير.

  1. سجّل قياسًا مرجعيًا بلوحة الأداء ودوّن FCP و LCP.
  2. أضف defer لكل السكربتات وضع أنماط الشاشة الأولى داخل الصفحة.
  3. حوّل الحركات إلى transform و opacity ثم أعد القياس وقارن.

معيار النجاح: انخفاض واضح في زمن أول رسم واختفاء الإطارات الطويلة أثناء التمرير.
